# Capability Map: Workbench `developer-support` and `operational-support`

Status: **approved.** Module specs follow in build order, one at a time, each reviewed before the next.

Scope: ship the `developer-support` (the default) and `operational-support` modes of the Workbench MCP server (`workbench mcp`) completely, plus `workbench` workspace setup. The onboarding modes (`operational-onboarding`, `developer-onboarding`) are out of scope here, but the shared modules below are designed so they can reuse them.

## Decisions this map rests on

- Rust, in the existing workspace, hexagonal layout: ports and use cases in `lib/engine` (no I/O), shared driven adapters in `lib/adapters`, and one binary crate, `services/cli`, that holds the driving adapters (the CLI and the MCP server) and any adapter only that binary needs. The templates the engine fills in live in `lib/engine/templates/`.
- **One binary, a background server.** There is no separate `workbench-mcp` executable: the MCP server is the `mcp` command group of `workbench` (its code is the `mcp` module of the `workbench` crate, `services/cli/src/mcp/`; there is no `services/mcp` crate). A server runs in the background, one per workspace and mode, on a Unix socket. AI platforms run `workbench mcp connect`, a stdio shim that relays to it. `workbench mcp start | stop | restart | status | logs` manage the server, and a restart does not disconnect a platform: the shim reconnects (for up to 90 seconds) and replays its handshake. Logs: every server start writes its own server log, and in `operational-support` every session also gets its own log file, which is the audit record; the directory is `logs.dir` in the server config (default `.workbench/logs`). `developer-support` writes server logs only, to the default directory. Log files are owner-only and never contain a secret. There is no network listener.
- **The default mode is `developer-support`.** `workbench mcp start --mode <mode>` picks a mode; without it the server runs `developer-support`, which needs no secrets and no production access. Operational access is always opt-in by naming `operational-support`.
- **Each mode loads only what it needs.** `developer-support` needs no secrets and no production access, only the graph and LSP. `operational-support` uses everything `developer-support` does (the graph and LSP, to speed up analysis and traversal) *plus* the operational modules and secrets, and requires the server config to exist and be valid *before* the server starts; if not, it exits with an error that says so.
- **Two configurations in one directory.** The `.workbench/` directory holds the configuration for the CLI, the MCP server and the memories, and is git-ignored entirely, so teammates create their own workspace config with `workbench`. The *workspace config* (`.workbench/config.yml`, written by `workbench`) lists the projects of a mono repo or of several repos, with each one's language and dependency manager. The *server config* (`.workbench/mcp/config.yml`) lists the contexts, a required `default_context` (so there is no guessing at start-up) and, for each context, the path of its own config file. Each context's config file (by default `.workbench/mcp/contexts/<name>.yml`) holds its code branch, connections and credentials. `workbench init` generates the server config and one template file per context (placeholders for credentials; never overwrites an existing file) and adds `.workbench/` to the project's `.gitignore`. A template with unfilled placeholders is not valid, so `operational-support` still refuses to start until it is completed.
- **Secrets:** may be written inline in a context config file or pulled from an environment variable whose name the same file gives (`<field>_env`); the variable wins when it is set. They are held as `secrecy` secrets from the moment they are read, and never printed, logged or returned by a tool. They are exposed only to open a connection. There is no pattern-based redaction: `secrecy` plus never exposing a value is the whole mechanism. Secret references are resolved by `core` (`SPEC-core.md`); the workspace config's `api_key_env` and `password_env` allow the variable name only.
- **Contexts** are `production`, `staging` and `testing`. All are **read-only**. Each has a code branch (the branch cherry-picked for the release that runs there) and its own VM and credentials: Workbench logs in over SSH and runs the commands there (`kubectl` and whatever else operations needs), and reaches PostgreSQL, Redis and Kafka through the VM (an SSH tunnel with local drivers, or the VM's own tools; configurable per connection). The first release logs in to the VM directly with a password, with no bastion host. In `operational-support` the graph, code reads and LSP see the active context's branch, kept as a separate git worktree per project (`workbench context sync`), so nobody's own working tree is touched. The context names are exactly these three; PostgreSQL and Redis can have several named connections per context.
- **Switching** contexts happens only on an explicit instruction from the user; the agent never switches on its own. The active context is per client session, and every new session starts in the server's start context (`workbench mcp start --context C`, default `default_context`). A switch asks the user to confirm through MCP elicitation, and first runs the connection check for the target context, refusing the switch if it fails; if the client does not support elicitation, the switch is refused and the user changes `default_context` and restarts. One server process holds all contexts.
- **A workspace is a set of projects.** Each project is an entry in the workspace config with a stable id, a path, a language, a dependency manager and, where needed, a virtual environment or activation command. Projects can be queried together: graph queries and search span every project by default and can be narrowed to one or several. LSP is activated per project and used at workspace level: a request about a file or symbol is routed to the language server of the project that owns it.
- **Per-project memory:** `.workbench/memory/<project-id>/` exists for every project in the workspace, and each starts with an `INIT-MEMORY.md` holding the project's initial context. Adding a project to the workspace creates its folder and file. A new `INIT-MEMORY.md` is seeded from context the project already has (for example its README, `CLAUDE.md` or `AGENTS.md`) and falls back to an empty template; which files count is decided in `SPEC-workspace.md`. To share the memories with a team later, un-ignore `.workbench/memory/` in the project's `.gitignore`.
- **Semantic meaning can be attached to the indexed AST.** A person or an agent can annotate a node (a project, file, class or function) with what it is for, the role it plays, the domain terms it uses, tags, and links to other nodes. Annotations are anchored to stable node ids, survive incremental re-indexing, and are marked stale (never silently dropped) when the node they describe changes or disappears. People add them with `workbench semantic …`; agents add them through the MCP tools. Annotations written by people are also mirrored to `.workbench/memory/<project-id>/annotations.yml`, so they survive if the storage backend is wiped; agent-written ones are not mirrored, since they can be regenerated. An LLM can also draft annotations, but only when it is configured in the workspace config (`semantic.llm`: provider — `copilot-cli`, `ollama` or `claude` — model, endpoint and, for `claude`, the *name* of the environment variable holding the API key; the key is never stored in a config file) **and** the person asks for it with a flag (`workbench index --annotate` or `workbench semantic generate`). Nothing is sent to an LLM otherwise.
- **The initial context of a project is four things:** the AST graph and the semantic annotations (both in the configured storage backend, SQLite or Memgraph, served through the MCP tools), the LSP, and the project's `INIT-MEMORY.md` for additional written context. Workbench does not generate context files inside projects.
- **A watcher keeps the index fresh.** `workbench watch` starts a monitored background process (a thread cannot outlive the CLI command, so the watching runs on a thread inside a detached process, managed like the MCP server) that re-indexes changed files as they change, including AI edits; `workbench watch stop` ends it. AI platforms can hook into it (start at session start, `watch flush` after an edit so the next query sees it, stop at session end), but hooks are installed only when asked, with their own command, `workbench platform hooks install`; `workbench platform setup` never installs them. The watcher never calls an LLM and never changes project files.
- **The CLI also builds the AST structures** (`workbench index`) and **updates them incrementally**: only files that changed are re-parsed, never the whole codebase, and what depends on them is re-linked. The MCP `reindex` tool uses the same incremental path.
- The **service graph** is built from the workspace projects with tree-sitter grammars per language. Cross-service connections come from parsing Dockerfiles, Docker Compose files and shared-library APIs.
- **Languages and files:** Python (poetry, uv); Angular with HTML, CSS, SCSS and TypeScript (Vite build; npm, pnpm, yarn or bun); YAML; Dockerfile; Docker Compose.
- The first **log source** is `kubectl` with configurable namespace.
- **Storage is configurable:** SQLite or Memgraph. The settings live in the workspace config (`storage` block), not the server config, because `developer-support` and the CLI need storage without the server config; a Memgraph password is referenced by environment variable name.
- Every tool call is recorded in the **audit log**, which is the per-session log file (`<logs.dir>/sessions/<session-id>.log`, JSON Lines, `operational-support` only). There is no separate copy in the storage backend. It is retrievable per session. Nothing is scrubbed by pattern; credentials never reach the log because they are never exposed.
- **LSP at project level and workspace level** is in the first release, in two parts: the MCP server runs language servers for the workspace's languages and exposes them as tools, and `workbench platform setup` configures the AI platform's own LSP integration. Both honour per-project settings such as a Python virtual environment, and each project's language server starts only when it is needed. `basedpyright` is the default for Python; the servers for the other languages (Angular and TypeScript, HTML, CSS, SCSS, YAML, Dockerfile, Compose) are chosen in `SPEC-lsp.md`. The LSP settings are part of the workspace config: an optional `lsp` block per project (enabled, server, launch command override, server settings) and optional per-language defaults for the whole workspace; a project's value wins over the workspace default, which wins over the catalog default. The workspace config also says how to activate each project's environment (for Python, a venv path, `poetry run` or `uv run`; for Angular, the project's `node_modules` through its package manager), and the platform LSP config is configurable per project with that activation command; its file format per platform is decided in `SPEC-platform-setup.md`.
- **Resolved execution flows are remembered**, only once you confirm the fix, and combined into a complete orchestration flow of the system. The storage backend is the working store, used to query and combine flows; on confirmation, one file per flow is also written to `.workbench/flows/` and the combined orchestration flow is regenerated there. Because `.workbench/` is git-ignored the files stay local, so sharing flows across a team depends on a shared backend, such as a shared Memgraph. This is part of the first release.
- **Tools are not defined yet.** Tool names below are candidates from the product brief; each module spec defines its tools.

## Shared with the other modes

- **Used by `developer-support`**, the default mode (no secrets, no production access): `workspace`, `core`, `storage`, `graph`, `semantic-layer`, `lsp`, `dev-support`, and `platform-setup` and `index` on the CLI side. It must start without a server config.
- **Reused by the onboarding modes:** `graph`, `semantic-layer`, `lsp`, and the read paths of `incidents` and `flow-memory`.
- **`operational-support` uses all of the above** (graph, semantic layer and LSP, for faster analysis and traversal) **plus** the operational-only modules: `contexts`, `audit`, `operations`, `data`, `execution-flow`, `flow-memory`, `incidents`, `agent-prompts`.

## Boundaries between modules

- `workspace` is the only contract between `cli` and the MCP server: the CLI writes it (config and memory folders), the server reads it.
- Project scope is a `workspace` concept: every module that queries projects takes a project id list and defaults to all of them.
- `INIT-MEMORY.md` is human-editable context. `dev-support` serves it to the agent (with the graph and annotations) through `project_context`; `semantic-layer` reads it and may suggest additions, but nothing overwrites what a person wrote.
- Every tool has one of three kinds: `observe` (reads code, the index or an observed system), `record` (writes only to Workbench's own storage or files) or `edit` (changes files inside a registered project's directory). No tool changes an observed system (a running environment or its datastores), in any mode. Only `developer-support` registers `edit` tools; `operational-support` has none, so a fix there is a recommendation. `edit` tools ask for no confirmation of their own: the AI platform's permission prompts apply. `core` refuses to register a tool without a kind.
- `developer-support` never reads the server config, so it starts without one.
- Only `contexts` reads credentials and hands resolved settings to tools; tools never read secrets themselves. Secrets are `secrecy` values everywhere and are exposed only at the point a connection is opened.
- The agent never switches context unless the user explicitly instructs it; the `contexts` spec defines how the server checks that.
- Connection checks exist only for operational modes and only for the context in use. `workbench context check [--context C]` checks one context's connections (kubectl, PostgreSQL, Redis, Kafka) and reports each as ok, failed or skipped (it proves the connection works; it does not verify that credentials are read-only, which the tools enforce); `workbench mcp start --mode operational-support [--context C]` runs the same check first and refuses to start if it fails. There is no health monitoring while the server runs and no degraded state; a tool whose connection has gone down returns an error naming the system. `developer-support` makes no connection checks.
- Read-only is an invariant of every context, not a production special case. `operations` and `data` specs must say how it is enforced (for example a SQL allowlist, or a read-only role) and test it.
- `storage` exposes ports; `graph`, `semantic-layer`, `flow-memory` and `incidents` do not know whether the backend is SQLite or Memgraph.
- All indexing runs (`workbench index`, `workbench watch`, the MCP `reindex` tool) share one lock, so only one run writes at a time. The watcher shares the incremental use case with `index` and adds no rules of its own.
- Incremental indexing lives in `graph` and runs through `engine` ports, so `workbench index` and the MCP `reindex` tool share one code path. Parsed data is keyed by project and file content hash; an unchanged file is never parsed again. The CLI and the server may touch the same storage, so the `storage` spec must define safe concurrent access (for example SQLite in WAL mode).
- `graph` owns node identity: a node id is stable across incremental re-indexing (view, project, relative path, qualified name, kind) and carries a content hash. A **view** is one checkout of a project: its own working tree (used by `developer-support`) or a context's branch worktree (`context:<name>`), so the same file on two branches gives two sets of nodes. `semantic-layer` owns annotations and anchors them to those ids; when a node's hash changes its annotations become stale, and when the node disappears it is kept as an orphaned tombstone so its annotations stay visible. Nothing is deleted automatically; `workbench semantic prune` removes stale annotations and orphaned tombstones on request.
- `semantic-layer` updates the mirror whenever a person adds, revises, retracts or prunes an annotation; the mirror is the recovery copy when the backend is empty.
- LLM-drafted annotations are recorded as written by an agent, with the model name. They only target nodes that are new or changed and have no person-written annotation, and they never overwrite one. Only indexed source nodes are ever sent to the LLM, never other files.
- Annotations written by a person are never overwritten or removed by an agent; agents can propose revisions.
- `graph` owns what a "service boundary with evidence" is; `operations`, `execution-flow` and `semantic-layer` consume it.
- A session is one connected client, identified by a token its shim generates; it survives a server restart. Per-client state (the active context, elicitation prompts) is per session.
- `audit` writes the per-session log file, which is the only audit record. It records every tool call with its session and the active context, only appends, and is read per session. The event format and the session boundary are defined in its spec.
- `flow-memory` builds on the session log (the audit trail) of a session and on `execution-flow` results; it does not call production systems itself. It saves a flow only after the user confirms the fix.
- Kafka reads must not join a consumer group or commit offsets, so reading never changes the system's state.
- `lsp` runs per project using the language and environment in the workspace config; it needs no secrets. `platform-setup` reuses its language server catalog, so the server and the platform use the same servers and settings.

## Roadmap (not in the first release)

- **MCP over Streamable HTTP**, as an opt-in second listener (`workbench mcp start --http`) next to the Unix socket: bound to `127.0.0.1` only, with a bearer token and `Origin` checking, so HTTP-capable platforms can connect without the stdio shim. The socket and shim stay the default.
- **SSH extras**: jump hosts (bastions) and key or ssh-agent login. The first release logs in directly with a password.
- **Log retention**: deleting or archiving old server and session logs (for example `workbench mcp logs --prune`). For now they are kept until a person removes them.
- `workbench project scan <DIR>`: find the projects under a directory and add them in one go. For now projects are added one at a time.
